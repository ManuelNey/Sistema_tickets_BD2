JUSTIFICACIÓN: PREVENCIÓN DE SQL INJECTION MEDIANTE PARAMETRIZACIÓN
=====================================================================

1. INTRODUCCIÓN
---------------
La implementación de UsuarioRepository utiliza la técnica de parametrización de queries SQL,
que es el método más efectivo para prevenir ataques de SQL injection según OWASP.

2. COMO FUNCIONA LA PARAMETRIZACIÓN EN LA IMPLEMENTACIÓN
---------------------------------------------------------

En el código UsuarioRepository.cs se utiliza:

    cmd.CommandText = @"SELECT * FROM persona WHERE mail = @mail";
    cmd.Parameters.AddWithValue("@mail", mail);

Esto separa el código SQL de los datos en DOS PARTES DISTINTAS:
- Parte 1 (SQL): "SELECT * FROM persona WHERE mail = @mail"
- Parte 2 (DATOS): mail = "juan@test.com"

El placeholder @mail actúa como referencia, NO como concatenación de strings.

3. POR QUÉ PREVIENE SQL INJECTION
----------------------------------

ESCENARIO DE ATAQUE SIN PARAMETRIZACIÓN (Vulnerable):
    string mail = "' OR '1'='1";
    string query = $"SELECT * FROM persona WHERE mail = '{mail}'";
    // Query resultante: SELECT * FROM persona WHERE mail = '' OR '1'='1'
    // Esto retorna TODOS los registros porque '1'='1' siempre es verdadero
    // ¡INJECCIÓN EXITOSA! ❌

CON PARAMETRIZACIÓN (Seguro):
    string mail = "' OR '1'='1";
    cmd.CommandText = "SELECT * FROM persona WHERE mail = @mail";
    cmd.Parameters.AddWithValue("@mail", mail);
    // Npgsql trata el valor como LITERAL, no como código SQL
    // La query busca un mail exacto con ese valor literal
    // Resultado: NO se encuentra (porque ese mail no existe)
    // ¡INYECCIÓN BLOQUEADA! ✓

4. MECANISMO DE PROTECCIÓN
---------------------------

Cuando se usa parametrización con Npgsql:

a) PARSING: PostgreSQL primero interpreta la estructura SQL (@mail es solo un placeholder)
b) COMPILACIÓN: La query se prepara antes de recibir datos
c) BINDING: Los valores se adjuntan como DATOS, no como código
d) ESCAPING AUTOMÁTICO: Npgsql escapa caracteres especiales (',",\,etc.)

El driver Npgsql maneja automáticamente:
- Comillas simples (') → Escapadas
- Comillas dobles (") → Escapadas
- Barras invertidas (\) → Escapadas
- Comandos SQL embebidos → Tratados como strings literales

5. APLICACIÓN EN TODO EL CÓDIGO
--------------------------------

Todas las queries en UsuarioRepository.cs usan parametrización:

CreateAsync():
    INSERT INTO persona (...) VALUES (@mail, @nombre, @apellido, ...)
    - 12 parámetros separados del SQL
    - Cada valor escapado individualmente

AuthenticateAsync():
    SELECT p.mail, p.nombre, ... WHERE p.mail = @mail
    - El mail se valida como parámetro, no como código

GetByMailAsync():
    SELECT ... WHERE p.mail = @mail
    - Parametrizado para prevenir acceso no autorizado

ExistsAsync():
    SELECT 1 FROM persona WHERE mail = @mail LIMIT 1
    - Parametrizado incluso en checks de existencia

6. COMPARACIÓN CON ALTERNATIVAS INSEGURAS
-------------------------------------------

❌ CONCATENACIÓN (VULNERABLE):
    cmd.CommandText = "SELECT * FROM persona WHERE mail = '" + mail + "'";
    Riesgo: SQL injection directo

❌ STRING.FORMAT (VULNERABLE):
    cmd.CommandText = string.Format("SELECT * FROM persona WHERE mail = '{0}'", mail);
    Riesgo: SQL injection si mail contiene caracteres especiales

❌ INTERPOLACIÓN DE STRINGS (VULNERABLE):
    cmd.CommandText = $"SELECT * FROM persona WHERE mail = '{mail}'";
    Riesgo: SQL injection en tiempo de ejecución

✓ PARAMETRIZACIÓN (SEGURO):
    cmd.CommandText = "SELECT * FROM persona WHERE mail = @mail";
    cmd.Parameters.AddWithValue("@mail", mail);
    Protección: SQL injection imposible

7. NORMA OWASP
--------------

OWASP Top 10 2021 - A03:2021 – Injection

La parametrización es RECOMENDADA como CONTROL PRIMARIO contra SQL injection.

Cita: "Prepared statements ensure that an attacker is not able to change the intent
of a SQL statement"

La implementación sigue esta recomendación al 100%.

8. CONFIRMACIÓN TÉCNICA
------------------------

Npgsql (versión 8.0.4 usada en el proyecto):
- Implementa "Prepared Statements" automáticamente
- Separa análisis sintáctico de vinculación de datos
- Proporciona escaping de caracteres según estándar PostgreSQL
- No permite inyección de código SQL en parámetros

9. CONCLUSIÓN
-------------

La implementación de UsuarioRepository previene SQL injection porque:

✓ Usa parametrización en el 100% de las queries
✓ Separa código SQL de datos
✓ Npgsql escapa automáticamente valores de entrada
✓ Cumple con normas OWASP
✓ No concatena strings en queries
✓ Cada parámetro se trata como valor literal

Por lo tanto, la implementación ES SEGURA contra ataques de SQL injection.
